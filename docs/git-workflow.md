# Git 작업 규칙

이 저장소는 `main` + 짧은 작업 브랜치 + Pull Request 방식으로 관리한다. 개인 프로젝트이므로 상시 `develop` 브랜치를 추가하지 않는다.

## 새 작업

1. 먼저 `git status`로 미커밋 작업을 확인한다. 다른 작업이 있으면 덮어쓰거나 무조건 stash하지 않고 해당 작업 브랜치를 유지한다.
2. 깨끗한 `main`에서 `git pull --ff-only`로 원격을 맞춘다.
3. 주제별 브랜치 `codex/<topic>`를 만든다. 예: `codex/fix-login-validation`.
4. 한 커밋에는 한 목적만 담는다. 파일 전체가 아니라 필요한 파일/구간을 골라 stage하고 `git diff --cached`로 확인한다.
5. 관련 검사와 빌드를 실행하고 PR 본문에 실행 명령·결과·미검증 범위를 적는다.
6. `git push -u origin <branch>` 후 `main`을 대상으로 PR을 만든다.
7. CI와 변경 내용을 확인한 다음 병합한다. 검증 실패를 숨기거나 검토 없이 강제 병합하지 않는다.
8. 병합 후 로컬 `main`에서 `git pull --ff-only`한다. 병합된 작업 브랜치는 상태를 확인한 뒤 정리한다.

## 커밋 메시지

`<type>(<scope>): <변경 결과>` 형식. 설명은 한국어를 사용할 수 있다.

- `feat`: 새 기능
- `fix`: 동작 오류 수정
- `refactor`: 기능을 유지한 구조 변경
- `test`: 테스트 변경
- `docs`: 문서
- `ci`: 자동 검사
- `chore`: 도구·관리 작업

예: `feat(language): 전체 단어 가리기 제공`, `fix(auth): 만료 세션 처리 수정`.

코드·회귀 테스트·해당 기능의 사용법/결정 기록은 같은 커밋에 둘 수 있다. unrelated 변경, 생성물, 개인 자료를 끼워 넣지 않는다. 커밋은 가능한 한 그 시점만 체크아웃해도 빌드되어야 한다.

## PR과 병합

한 PR은 하나의 검토 가능한 목적을 다룬다. 평소 작은 기능 PR은 squash merge를 사용할 수 있다. 기능별 커밋 여러 개로 나눈 과거 미커밋 작업 정리 PR은 **Create a merge commit**으로 커밋 경계를 보존한다. squash와 merge를 혼용해 같은 PR을 다시 합치지 않는다.

PR 템플릿에 문제·최종 동작·검증·남은 한계를 적는다. 혼자 관리하는 동안 필수 승인자를 임의로 지정하지 않는다. 브랜치 보호나 ruleset은 저장소 관리자가 별도 설정하며 이 문서/CI가 강제 보호 설정을 의미하지 않는다.

이미 공유한 커밋 이름을 고치기 위해 main을 rebase하거나 force-push하지 않는다. 취소는 새 `revert` 커밋/PR로 처리한다. 미공유 작업 브랜치의 amend/rebase는 다른 사람이 사용하지 않는 것이 확인된 경우에만 사용한다.

## 데이터 경계

`.env`, 자격 증명, 개인 메모/백업, DB, 생성 로그, 빌드 산출물, 의존성 폴더를 stage하지 않는다. `.gitignore`는 이미 추적된 파일을 제거하지 않으므로 stage된 파일 목록을 항상 확인한다. 실수로 비밀이 올라갔다면 우선 해당 자격 증명을 폐기/교체하고 별도의 이력 정리 절차를 논의한다.

## 현재 과거 이력 정리의 범위

기존 원격 커밋을 다시 작성하지 않는다. 대량 미커밋 작업은 실제 의존성에 맞는 기능 단위로 분리하고 각 단계의 빌드를 검사한다. 과거 커밋 날짜·작성자·메시지를 허위로 재구성하지 않는다. 이후의 새 작업부터 위 규칙을 적용한다.
