ARIA Home AI details

01 project

말 한마디가 실제 일정과 알람으로 이어지는 AI 비서

ARIA는 단순 챗봇이 아니라, 음성 입력을 받아 일정, 알람, 브리핑, 날씨, 이동 준비로 연결하는 개인 홈 AI 비서입니다. 처음에는 PC에서 시작했지만, 운영을 위해 서버와 클라이언트 역할을 나누었습니다.

problem

일정, 알람, 메모 요청을 매번 직접 입력해야 해서 자연어 명령을 실제 동작으로 연결하는 흐름이 필요했습니다.

solution

FastAPI 서버에서 요청을 분류하고, 필요한 경우 AI API를 호출해 응답 생성과 저장 동작을 분리했습니다.

my role

API 서버, 자연어 의도 분류, AI 응답 처리, 일정/알람 저장 흐름을 직접 구현했습니다.

result

음성 또는 자연어 입력으로 일정 조회, 알람 설정, 메모 저장이 가능한 개인 AI 비서 기능을 만들었습니다.

02 nlp

형태소 분석기 없이 한국어 명령을 분류했습니다.

KoNLPy나 Mecab 같은 형태소 분석기를 붙이지 않고, scikit-learn의 TF-IDF와 Naive Bayes로 가벼운 한국어 의도 분류기를 만들었습니다. 한국어 어절 안의 문자 패턴이 의미를 담고 있다는 점을 이용했습니다.

feature
char_wb n-gram 2~4 + TF-IDF

한국어는 조사와 어미가 붙기 때문에 단어 경계가 애매합니다. 문자 단위 n-gram을 쓰면 “예약해줘”, “예약”, “바꿔줘”처럼 어절 안에 숨어 있는 패턴을 형태소 분석 없이 잡을 수 있습니다.

classifier
Multinomial Naive Bayes

학습 데이터가 많지 않은 개인 프로젝트 단계라, 작고 빠르게 학습되는 Naive Bayes를 선택했습니다. 서버 기본 실행은 룰 기반으로도 가능하게 두고, 모델이 있으면 ML confidence를 함께 반영합니다.

override
Action Override 레이어

“치과 예약 4시로 바꿔줘”처럼 명사 점수가 높아 일정 추가로 오분류되는 문제를 보고, “바꿔줘/취소해줘” 같은 액션 동사를 명사보다 먼저 보는 override 레이어를 추가했습니다.

03 cost

GPT는 마지막에만 쓰도록 처리 경로를 나눴습니다.

모든 요청을 GPT로 보내면 구현은 쉽지만 매일 쓰는 개인 비서에는 비용과 지연 시간이 부담입니다. 그래서 결정론적 룰, ML 분류기, GPT 폴백을 역할별로 나누고, 유사 질문은 캐시로 재사용했습니다.

filter
Rule - ML - GPT 3단 필터

Rule은 동사 기반으로 즉시 처리하고, ML은 학습된 표현을 10ms 이하로 분류하며, GPT는 정말 애매한 요청만 맡깁니다. 내부 테스트 18개 기준 GPT 필요 케이스는 2개였습니다.

cache
QA 시맨틱 캐시

임베딩 API를 새로 쓰지 않고, NLP 파이프라인에서 쓰는 TF-IDF 벡터라이저를 재활용해 유사 질문을 찾습니다. 유사도 0.82 이상이면 GPT 호출 없이 이전 답변을 반환합니다.

side channel
<!-- SAVE:... --> 구조화 마커

사용자에게 보이는 답변 말투는 유지하면서, 저장 가능한 목록은 HTML 주석 마커로 백엔드에 전달합니다. UX를 건드리지 않고 저장 동작을 추가한 사이드채널입니다.

04 server

클라우드 서버비를 쓰기 전에, Mac mini를 홈 서버로 운영했습니다.

개인 프로젝트 단계에서 매달 서버비를 쓰기보다 집에 있는 Mac mini를 활용했습니다. Docker로 서버를 올리고, PostgreSQL과 백그라운드 스레드를 붙여 계속 켜둘 수 있는 형태를 만들었습니다.

runtime
알람 워커와 프로액티브 스케줄러

알람 워커는 주기적으로 DB를 확인하고, 스케줄러는 중요한 일정 전 사전 알림을 만듭니다.

watchdog
죽은 스레드 자동 복구

알람이나 스케줄러 스레드가 죽었는지 감시하고, 문제가 생기면 다시 시작하도록 구성했습니다.

backup
백업과 서버 진단 API

DB 백업, 런타임 상태, TTS 브리지 상태 등을 확인할 수 있는 관리용 API를 추가했습니다.

05 bug fixing

기억에 남는 버그 해결 사례

실제로 쓰면서 만난 버그들은 설계 단계에서 예상하지 못했던 것들이었습니다. 특히 NLP 분류기에서 발생한 문제들은 단순 키워드 매칭의 한계를 직접 경험하게 해줬습니다.

problem
공백 정규화 후 키워드 중복 카운트

”할일”과 “할 일”을 공백 제거 후 비교하면 같은 문자열이 되는데, 둘 다 키워드 목록에 있어 TASK_ADD가 4점, TASK_QUERY가 3점으로 잘못 분류됐습니다.

solution
인텐트별 seen_clean 셋으로 중복 제거

각 인텐트 채점 시 공백 제거된 키워드를 seen_clean 셋에 추가해, 같은 문자열이 여러 번 매칭되더라도 한 번만 점수에 반영되도록 수정했습니다.

problem
동사 키워드 가중치가 명사 누적에 짐

”바꿔줘”(3글자 → 가중치 2)보다 “치과”(2pt) + “예약”(2pt) = 4점이 높아, “치과 예약 바꿔줘”가 EVENT_UPDATE가 아닌 EVENT_ADD로 분류됐습니다.

solution
_ACTION_OVERRIDES 레이어로 선행 확정

수정·취소·완료 같은 액션 동사가 감지되면 키워드 점수 계산 전에 인텐트를 확정(confidence 0.88)하는 별도 레이어를 추가해 명사 누적 문제를 구조적으로 차단했습니다.

problem
GPT 응답에서 저장할 항목만 뽑기 어려움

”파스타 만들려면 뭐 필요해? 그거 메모해줘”처럼 자유 형식 GPT 답변에서 재료 목록만 구조화해 DB에 저장해야 했습니다. JSON 모드를 쓰면 자연스러운 대화체가 깨집니다.

solution
숨겨진 HTML 주석으로 구조 데이터 채널 분리

GPT 프롬프트에 목록이 있으면 답변 끝에 <!-- SAVE:제목|항목1,항목2 --> 마커를 붙이도록 지시하고, 서버에서 파싱 후 제거해 사용자에겐 자연스러운 텍스트만 전달했습니다.

problem
”그거 메모해줘”에서 '그거'가 무엇인지 모름

HTTP는 stateless라 직전 GPT 응답이 다음 요청에 전달되지 않습니다. “그거”가 가리키는 내용을 서버가 알 수 없었습니다.

solution
세션 인메모리 saveable + history 역순 파싱

SAVE 마커 파싱 시 _session_saveable[session_id]에 저장해두고, CONTEXT_SAVE 인텐트가 오면 해당 세션 항목을 꺼냅니다. 세션 데이터가 없으면 history를 역순으로 탐색해 직전 assistant 메시지에서 목록 라인을 추출합니다.

Flow-Work details

01 project

문서, 화이트보드, 코드 작업을 한 화면에서 다루는 협업 워크스페이스

Flow-Work는 단순 문서 앱이 아니라, 실시간 문서 편집, 화이트보드, 회의록, Git 작업 흐름, AI 어시스턴트를 한 워크스페이스 안에 묶은 프로젝트입니다. 프론트엔드부터 NestJS 서버, FastAPI AI 서버, Supabase DB, Electron 데스크톱 앱까지 직접 연결했습니다.

problem

협업 환경에서 문서 상태가 늦게 반영되거나 여러 화면이 같은 데이터를 다루며 동기화 지연과 충돌 위험이 생겼습니다.

solution

WebSocket과 Yjs를 활용해 문서 변경 사항을 실시간으로 공유하고, Supabase 기반 저장 구조와 연결했습니다.

my role

프론트엔드 작업 공간 UI, 다중 문서 창, 실시간 협업 편집 흐름 일부를 구현하고 리렌더링 문제를 개선했습니다.

result

여러 사용자가 동시에 문서를 편집해도 변경 사항이 실시간으로 반영되는 협업 환경을 구성했습니다.

02 multi window

다중 문서 창에서 에디터 리렌더링 문제를 줄였습니다.

여러 문서를 동시에 띄우면 창 이동, 리사이즈, 포커스 변경이 계속 발생합니다. 처음에는 이런 UI 상태 변화가 무거운 문서 에디터까지 흔들어 다중창 사용감이 불안정했습니다.

problem
창 상태와 문서 편집 상태가 같이 흔들림

창의 위치와 z-index가 바뀔 때 내부 BlockNote/TipTap 에디터까지 영향을 받아 불필요한 렌더링이 생겼습니다.

solution
창 메타데이터와 문서 세션 분리

Zustand store에서 창의 위치/크기/활성 상태와 문서 세션 상태를 나누고, 실제 cleanup은 창을 닫을 때 일어나게 했습니다.

performance
React.memo + requestAnimationFrame

창 컴포넌트를 memo 처리하고 드래그/리사이즈 좌표 업데이트를 requestAnimationFrame으로 묶어 렌더 빈도를 줄였습니다.

03 whiteboard

화이트보드 이미지가 새로고침 후 깨지는 문제를 추적했습니다.

Excalidraw와 Yjs를 붙이면 도형 동기화만으로 끝나지 않습니다. 이미지 파일은 storage에 저장되고, scene은 Yjs로 공유되기 때문에 두 데이터의 타이밍이 어긋나면 다른 사용자가 placeholder만 보게 됩니다.

problem
scene과 file source의 원자성 문제

이미지 element는 먼저 공유되지만 실제 파일 경로는 나중에 기록되어 refresh나 늦은 접속에서 복원 순서가 꼬일 수 있었습니다.

fix
S3 기반 asset 저장/복원 흐름 정리

파일 저장 키, asset registry, 복원 책임을 분리하고 orphan asset 정리까지 고려해 구조를 개선했습니다.

learning
patch보다 구조 전환이 필요한 문제로 판단

단순 로컬 snapshot 보정보다 binding 중심 sync와 fileId = storage key 계약으로 가야 한다는 리팩토링 방향을 문서화했습니다.

04 ai search

문서를 AI가 검색할 수 있도록 projection과 embedding 흐름을 나눴습니다.

협업 문서는 Yjs 상태로 저장되기 때문에 AI가 바로 검색하기 어렵습니다. 그래서 문서 상태를 plain text와 chunk로 변환하는 projection 단계와, 검색용 embedding 단계를 분리했습니다.

pipeline
projection job / embedding job 분리

문서 변경 후 projection을 만들고, 해당 chunk 기준으로 embedding 작업을 큐에 넣는 흐름을 구성했습니다.

freshness
stale projection 갱신

AI 검색 전에 projection이 오래된 경우 최신 문서 상태로 다시 갱신하도록 해 검색 결과의 신뢰도를 높였습니다.

cost
기존 embedding 재사용

이전 projection과 같은 text hash를 가진 chunk는 embedding을 재사용해 불필요한 외부 API 호출을 줄이는 방향으로 설계했습니다.

05 workflow

권한, 문서 고정, Git 작업 흐름까지 워크스페이스에 붙였습니다.

협업 도구는 편집만 되면 끝이 아니라 누가 보고, 누가 수정하고, 어떤 문서를 고정할 수 있는지까지 필요했습니다. 또 프로젝트 코드 작업을 위해 로컬 Git 흐름도 작업 공간 안으로 가져왔습니다.

permission
Space별 읽기/쓰기/승인 권한

멤버 태그 기반으로 읽기, 쓰기, freeze 승인 권한을 나눠 공간별 협업 규칙을 설정할 수 있게 했습니다.

freeze
문서 고정 요청과 승인 흐름

작업 중인 문서를 고정본으로 만들 때 요청, 승인, 반려 상태를 나눠 문서 변경 흐름을 관리했습니다.

git
로컬 Git Agent 연동

commit, diff, merge request review를 워크스페이스 안에서 확인할 수 있도록 로컬 Git Agent와 Electron 앱 흐름을 연결했습니다.
